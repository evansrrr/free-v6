## 2. 复核新发现

### G1（P0）settings.json 损坏时 reset 必然失败，恢复路径是闭环

`resetSettings`（`main.go:466`）通过 `updateSettings` 写默认值，而 `updateSettings`
（`main.go:1222`）在 `loadSettings` 失败时直接返回
`settings.json 无法解析，请在设置中重置`。也就是说：

```
PUT /settings → 500 "请在设置中重置"
POST /settings/reset → 500 "settings.json 无法解析，请在设置中重置"
```

用户唯一的自救入口恰好被同一段逻辑挡住。v2 只写了"顺序反转"，没发现这条。

**处置**：reset 走 `overwriteSettings`（不读旧文件，直接原子写默认值）。
`updateSettings` 的"拒绝覆盖坏文件"语义保持不变——它保护的是常规保存，
reset 的职责就是把坏文件换掉。

### G2（P1）并发导入链式/备用会两个都开，单次导入也可能开出非法组合

两个 handler 都是"读 settings → 判断另一个模式是否开着 → 写文件 → 翻开关"，
判断在锁外：并发导入时双方都看不到对方，最后 `ChainEnabled` 与 `CloudEnabled`
同时为 true。启动时才会以 `400 不能同时启用` 暴露，用户看到的是"点一次导入，
下次启动就打不开"。

另外 `chainImport` **完全不检查** `CloudEnabled`（`cloudImport` 检查了反向），
单独一次导入就能造出非法组合。

**处置**：`configMu` 把"互斥检查 + 写内容 + 翻开关"收成一个事务；两个 handler
在锁内用同一段逻辑检查对方开关，冲突返回 409。

### G3（P1）内容文件截断后，错误信息指向错误的操作

崩溃/断电留下半个 YAML 时，`startProxy` 报 "解析链式代理失败"，而用户的直觉
是"重新导入"——可以自愈，但 `os.WriteFile` 的窗口完全没必要存在。

**处置**：两处改用 `writeFileAtomic`（临时文件 + fsync + rename）。

### G4（P1）`api()` 的超时会被当成"端口不对"，再等一轮

`api()` 的 catch 对所有异常都回落 13335 重试一次。加了超时之后，一次 25s 超时
会再等 25s（最坏翻倍），用户看到的是"检查更新卡了 50 秒"。

**处置**：只对连接失败回落；`AbortError` 直接转成 `code=timeout` 的超时错误。

### G5（P2）切换节点失败后界面显示未生效的节点

`switchProxy` 不看 `resp.ok`，先改 `state.proxyGroup.now` 再渲染；PUT 失败
（内核忙/节点已删）时界面停在新节点，直到下一次 5s 轮询把它改回去。

**处置**：校验 `resp.ok`，成功才改状态；失败只记日志。

## 5. 兼容性与风险

- **接口语义不变**：新增的 409/超时错误码只在原本会失败或卡死的路径上出现。
- **离线门禁放宽**（F1）：维护者关闭开关后，长期离线客户端要等下次联网才生效。
  这是 v2 §8 D8 已拍板的取舍（资源保护开关，不是急停）。
- **锁序**：`configMu → settingsMu` 单向；`startProxy` 不取 `configMu`（只读文件），
  不会与导入互相阻塞。
- **回滚**：三组改动互不依赖，可单独回退；无数据格式变更。
