## 0. 结论

### 0.1 对 v2 批次 2 的判定

**方向成立，但按原样实施会踩两个死锁/挂死陷阱，且有三处边界没定。** B1–B9 的目标（统一停止、异常收尾、进程树归属）和关键取舍（Job 归 helper、验收边界改写）都对；问题集中在"锁"和"等待"上：

| # | 问题 | 后果 | 处置 |
|---|---|---|---|
| 1 | 会话锁若包住 Stop 又间接调用 Start | Win32 互斥量按**线程**重入，Go 的 goroutine 会换线程 → 自死锁（有界等待下表现为 60s 后莫名失败） | 锁只在最外层取一次；`Start` 与 `StopSession` 各自内部取锁，**禁止嵌套** |
| 2 | shutdown 与 `startProxy` 争 `h.mu` | shutdown 卡在锁上，"优雅退出"变"不退出" | 有界等锁（5s）；超时返回 409 且**不退出**，由壳侧兜底强杀 |
| 3 | shutdown 若用 `request.Context()` | 壳侧 1.5s 就放弃连接 → 热点还原被当场取消 | 收尾用 `context.WithoutCancel` + 固定预算 |
| 4 | `update_apply` 先发 shutdown 再置 `stopping` | 正常退出被 `Terminated` 分支判成崩溃：弹"组件异常"并 `exit(1)` | 先 `mark_helper_stopping()`，再发请求 |
| 5 | 父进程监视"PID 无效就禁用" | 启动竞态窗口里父已退出却被当成"不监视" → 永久孤儿 | **句柄打开成功即安全**（句柄钉住进程对象，不存在 PID 复用）；打不开就是父已退出 → 立即收尾 |
| 6 | 孤儿接管/启动期 `kill_stray` 的等待 | 8s 会让冷启动退化；0s 会打断旧 helper 的热点还原 | 3s，且只在"确实是孤儿 helper"时等 |

### 0.2 范围与非目标

**做**：B1–B9（共用 StopSession、会话锁覆盖停止段、shutdown 端点、父进程监视、helper 自有 Job、`MarkVerified(version)`、壳侧退出/更新门禁、孤儿接管等待、CLI 对齐）。
**不做**：Windows 服务化、Linux/macOS 的 Job 等价物、CLI 也纳入 Job（见 §9 D6）、给 `/status` 增加 Job 状态字段。

### 0.3 与 batch 1 的边界

批次 1 已让 `update_apply` 前的停免流由前端完成（`startUpdate()` 先 `stopProxyApi()`），所以壳侧 shutdown 是**第二道保险**；这一前提决定了它的预算可以压到 1.5s 而不影响正常路径。

## 3. 本轮复核发现的 8 个问题

### F1 会话锁不可嵌套（设计级）

Win32 命名互斥量的"重入"是**按线程**计的：同一线程再次 `WaitForSingleObject` 会立即成功并增加递归计数。Go 的 goroutine 不绑定线程，第二次获取很可能落在**另一个线程**上 → 阻塞到超时。

所以：
- 如果 `StopSession` 内部取锁、而它又调用了 `mihomo.Start`（或反过来），就会自死锁；有界等待只会把它变成"60s 后一个看不懂的错误"。
- 处置：**锁只在最外层取一次**。`Start` 保持"自己取锁、只包住检查→spawn→写 pid"；停止序列由 `StopSession` 的调用方（helper/CLI）通过 `Lock` 注入取锁，`StopSession` 内部**不得**调用 `Start`。
- 验收：`lifecycle.StopSession` 的 Options 里没有 `Start` 钩子（结构上杜绝嵌套）；`grep` 断言 `WithSessionLock` 只出现在两个调用点。

### F2 shutdown 与 `h.mu` 的争用

`startProxy` 持 `h.mu` 可达数十秒（等待就绪 15s + 热点切换 120s）。shutdown 若直接 `h.mu.Lock()`，用户点"退出"就会卡住。

处置：shutdown 用**有界等锁**（5s）。拿不到就返回 409 `{code:"busy"}` 且**不退出进程**——让壳侧按自己的预算强杀（此时强杀是正确兜底，因为 start 还在跑）。拿不到锁却硬退出，会把一次进行中的启动切成半截状态。

### F3 shutdown 的收尾不能被客户端断开取消

壳侧 `Exit` 只等 1.5s。若 handler 用 `request.Context()`，客户端一断开，`StopSession` 立刻被取消，热点还原做一半。处置：`context.WithoutCancel(request.Context())` + 固定预算（沿用 `stopProxy` 现有写法），并用 `sync.Once` 防止与父进程监视重复执行。

### F4 `stopping` 必须先置位

`main.rs:926` 的 `Terminated` 分支在 `!stopping` 时弹"组件异常"并 `app.exit(1)`。改成"先 shutdown 再等退出"后，若忘了置位，**一次正常更新会被判成崩溃**。处置：抽 `mark_helper_stopping()`，`update_apply` 与 `Exit` 在发请求前调用；`stop_helper` 复用同一函数。

### F5 父进程监视的语义（PID 复用不是问题）

- env `FREEV6_PARENT_PID` **缺失** → 不启用（旧壳兼容）。
- env 存在但 `OpenProcess` 失败 → **父已退出**，立即收尾（不是"禁用"）。
- 一旦句柄打开成功，它就钉住了父进程对象：父进程不可能被回收成别的进程，所以**不需要比对启动时间**，`WaitForSingleObject(handle, INFINITE)` 是安全的。

这条纠正了 v2 里"PID 无效时禁用"和"比对启动时间"的含糊表述：前者会漏掉启动竞态，后者是多余的。

### F6 等待预算：3s 而不是 8s

`listenOrTakeOver` 与壳侧 `kill_stray_helpers` 都在**冷启动关键路径**上。批次 2 之后旧 helper 有父监视，父死即自退（通常几十毫秒），所以 3s 足够；给 8s 只会让"上次崩溃后重启"多等 5s。

顺序也要定：壳侧先 `reap_stray_helpers(3s)`（等镜像名消失），再 `start_helper`。这样新 helper 绑定时端口通常已经空出来，`listenOrTakeOver` 的 kill 分支几乎不会走到。

### F7 Job 自加入失败必须可观测

`CreateJobObject` + `AssignProcessToJobObject(自己)` 在某些宿主里会失败（父 Job 不允许嵌套）。失败本身可接受（退化为"只把核心挂进 Job"），但**不能静默**：否则"杀 helper 会带走核心"这条保证会悄悄消失，而验收时又看不出来。处置：失败写 `helper.log` 一行（`helper: job self-assign failed: ...; falling back to core-only`），并在批次 2 的真机矩阵里用"父进程在 Job 中的启动方式"验证退化路径仍能挂住核心。

### F8 CLI 停止缺少关 TUN 的能力

现在 CLI `stop` 只杀进程，wintun 适配器与 auto-route 路由要等系统回收。补 `mihomo.ReadControllerSecret(stateDir)`；读不到就跳过并记日志（不阻断停止）。

## 5. 兼容性

### 5.1 版本矩阵

| 壳 | helper | 行为 |
|---|---|---|
| 新 | 新 | 全量：shutdown + 父监视 + Job + 更新门禁 |
| 新 | 旧 | shutdown 404 → 回落 `/proxy/stop`（6s）+ 杀进程；无 Job（旧行为）；门禁更严格 |
| 旧 | 新 | 旧壳直接杀；父监视不启用（无 env）；Job 仍保护核心；接口全兼容 |
| 旧 | 旧 | 与今天一致 |

### 5.2 协议与格式

| 资产 | 约束 |
|---|---|
| `/api/v1/shutdown` | 新增 POST，Bearer 鉴权；旧 helper 404/405 时壳侧回落 |
| `FREEV6_PARENT_PID` | 新增 env；缺失即禁用（不需要新参数） |
| pid / `.meta` | **不动**（Rust 内存卡片按 `u32` 直读） |
| `network-snapshot.json` | 只读；删除条件收紧（见 §6） |
| Win32 互斥量名 | `Local\FreeV6-MihomoStart` **保持不变**（跨版本互斥 ABI） |

### 5.3 唯一不可逆行为

helper 被终止时核心随 Job 退出。今天会留下"网络还能用但没人管"的孤儿核心；改后网络会短暂中断并等下次启动自愈。**必须在 CHANGELOG 写明**。

### 5.4 保证边界（沿用 v2 §4.5，补充两条）

| 场景 | 能保证 | 不能保证 |
|---|---|---|
| 正常退出（无免流） | 无残留 | — |
| 正常退出（有免流，先停止） | 网络还原、快照删除 | — |
| 杀壳 | helper 数秒内收尾；无残留进程；热点**通常**可还原 | helper 同时挂死时热点等自愈 |
| 杀 helper | 核心与临时子进程随 Job 退出 | 网络状态等自愈 |
| **启动中退出** | 壳侧 1.5s 后强杀；Job 关闭 | 这次启动可能停在半截，需下次启动自愈 |
| **Job 自加入失败** | 核心仍随 helper 退出 | 临时子进程（powershell 等）可能残留 |

## 6. 性能预算

| 路径 | 现状 | 上限 | 守护 |
|---|---|---|---|
| 冷启动 → `/status` 200 | 31ms（批次 1 实测 p50） | **+<5ms** | `scripts/boot-measure` |
| 启动期 `reap_stray_helpers` | 立即 kill | ≤3s，且仅孤儿场景 | 手册 + 日志 |
| `/proxy/stop` | 0.3–1.2s（无热点） | 不变 | `helper.log` stop 行 |
| 停止段锁持有 | 无锁 | ≈9s（关 TUN 4s + 退出 2s + 清路由 3s） | 日志 |
| 退出（无免流） | ≈0（kill） | ≤100ms | 壳侧计时 |
| 退出（helper 挂死） | ≈0 | ≤3s | 门禁测试 |
| 更新安装门禁 | 5s 固定等待 | 6s（shutdown）+ 6s（等退出），超时中止 | 测试 |
| 前台并发启停 | 无保护 | start 最多等一次 stop（≈9s） | 并发测试 |

**禁止项**：不得在 `RunEvent::Exit` 里做超过 1.5s 的阻塞；不得让 shutdown 请求的取消影响收尾；不得为了"少杀一次"把孤儿等待抬到 3s 以上。

## 8. 测试方案

### 8.1 自动化

| 层 | 用例 |
|---|---|
| `internal/lifecycle` | 顺序断言（还原→TUN→停核→重读→清路由→删快照）；还原失败仍停核且保留快照；停核失败不清路由；停止期间新核心已启动 → 跳过清路由/删快照；适配器未消失 → 继续停核并记录 |
| `internal/mihomo` | `MarkVerified(version)` 版本不匹配不写；`Prune` 删除失败保留 Previous；会话锁超时返回可读错误；Windows Job 真进程测试（CI windows-latest） |
| `cmd/freev6-helper` | shutdown 鉴权/方法/重复调用；父监视用子进程模拟（Windows）；`stopProxy` 走 `StopSession` 后行为不变 |
| `cmd/freev6` | `stop` 走同一模块（注入假实现断言顺序） |
| `src-tauri` | HTTP 响应解析（200/404/超时）；门禁超时分支不启动 NSIS |

| # | 场景 | 期望 | 观测点 |

## 9. 需要确认的事项

| # | 事项 | 推荐 | 影响 |
|---|---|---|---|
| D1 | helper 被终止时核心随 Job 退出（网络会短暂中断） | **是** | 用户可见行为变化，需写进 CHANGELOG |
| D2 | 退出时壳侧等待 1.5s + 3s 强杀 | **是** | 保证"关得掉"；极端情况下收尾不完整，等自愈 |
| D3 | 更新安装遇 helper 未确认退出 | **中止安装** | 宁可更新失败，不造混合构建 |
| D4 | 父监视在 env 缺失时禁用；env 在但句柄打不开即收尾 | **是** | 兼容旧壳，同时堵住启动竞态 |
| D5 | 会话锁上限 60s | **是** | 持有者挂死时不至于永久卡 UI |
| D6 | 是否把 CLI 也纳入 Job | **否** | CLI 被杀仍会留孤儿核心；记为已知限制 |
| D7 | `MarkVerified` 是否也在"手动强制更新"路径生效 | **是（同一条启动路径）** | 无额外成本 |
